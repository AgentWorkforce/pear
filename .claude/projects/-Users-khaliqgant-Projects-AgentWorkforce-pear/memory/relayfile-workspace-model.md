Pear assigns each project a `relayWorkspaceId` that is a client-generated `crypto.randomUUID()` (`src/main/store.ts:387`) and **never** creates/joins a real relayfile cloud workspace. Pear has no `createWorkspace`/`joinWorkspace`/`connectIntegration` calls. Consequence: every workspace-scoped cloud call (integrations connect AND the cloud-agent box/mount) targets a workspace that doesn't exist → integrations "Connect" fails, cloud-agent attach fails.

The correct path (the `relayfile integration connect` CLI flow) is the `@relayfile/sdk`:
`RelayfileSetup.createWorkspace()/joinWorkspace(id)` → `WorkspaceHandle.connectIntegration(provider)` → returns Nango `{ connectLink, connectionId, alreadyConnected }` → open `connectLink` → `handle.waitForConnection(provider, { connectionId })`. Disconnect via `handle.disconnectIntegration`. See `node_modules/@relayfile/sdk/dist/setup.d.ts` and the CLI `relayfile/cmd/relayfile-cli/main.go` `runIntegrationConnect` (~line 1894).

Decision (Khaliq, 2026-05-21): use **one account-wide relayfile workspace** shared across all projects (not per-project). Integrations connect once at account level; per-project visibility toggle. This is captured in `specs/05-integrations-connect.md` (not yet built) and supersedes the per-project workspace assumption in specs 01 and [[cloud-agent-semantics]] / 04.

SDK provider whitelist (resolved): `@relayfile/sdk@0.7.23` (also the latest in `../relayfile`) hard-validates `connectIntegration`/`waitForConnection`/`disconnectIntegration` against a frozen 6-provider whitelist via `assertProvider` (`setup.ts:1178`) — narrower than the active set. Decision (no SDK bump): call the endpoints those wrappers call directly through the public `WorkspaceHandle.requestJson` (POST `integrations/connect-session` with `{ allowedIntegrations: [provider] }`, GET `integrations/{provider}/status`, DELETE `integrations/{provider}`); the cloud routes are provider-generic. RelayfileSetup auth = pear cloud token (`accessToken: () => auth.accessToken`, like `cloud-agent.ts:706`). relayfile workspace (account-wide, filesystem) and the messaging broker (per-project, via `/api/v1/sandboxes` + `/terminal` apiKey) are orthogonal — `joinWorkspace`'s relaycastApiKey is ignored. Provider id map is identity except `gmail→google-mail` (slack stays `slack`). specs/04 and specs/05 now contain no open questions.

Done & working (2026-05-21): integrations catalog renders Nango logos (`iconUrl` via `https://app.nango.dev/images/template-logos/{slug}.svg`, generated by `scripts/build-integrations-catalog.mjs`; slug overrides gmail→google-mail, teams→microsoft-teams, x→twitter) and is filtered to the 9 active cloud providers via `ACTIVE_PROVIDERS` in `src/main/integrations.ts` (mirrors non-deprecated relayfile providers in `cloud/packages/web/lib/integrations/providers.ts`). Pear provider id `gmail` maps to relayfile/nango `google-mail`.
